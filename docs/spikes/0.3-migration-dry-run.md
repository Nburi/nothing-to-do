# Spike 0.3 · Migration dry run

Refactor plan step 0.3 (R8, risk C6). Tooling built 2026-11-06 on `feature/migration-rehearsal`.

**Question:** can we run the refactor's migrations on a copy of production and prove that no row
and no value is lost?
**Gate:** a dry run on a production copy loses zero rows.

## What exists now

Two read-only commands. They work on whatever database the app is pointed at.

```bash
php artisan app:rehearsal-snapshot before --user=<your email>
php artisan migrate
php artisan app:rehearsal-snapshot after --user=<your email>
php artisan app:rehearsal-compare before after
```

- **Snapshot** = per table the row count and, per row and column, a short hash of the value.
  Never the values, so the file (`storage/app/rehearsal/*.json`, git-ignored) contains no readable
  user data. `--user` adds a spot check: how many rows of that account are in each table.
- **Compare** fails (exit 1) on anything that could mean lost data: fewer rows, a row id that is
  gone, a changed value in a column that existed before, a dropped table or column, a copied column
  that does not match its source. New tables, columns and rows are notes, not problems.
- Options for the planned two-step migrations:
  - `--same=tasks.deadline:tasks.hard_deadline` the new column must hold exactly the old values
  - `--allow-dropped=tasks.deadline` for the later drop step
  - `--ignore=tasks.list` for a column a migration is *meant* to change

Tests: `tests/Feature/Commands/MigrationRehearsalToolTest.php` (10).

## Tried on a copy of the local dev database

Copied `database/database.sqlite` to a temporary file and ran the full cycle there (the original
file was not touched): 41 tables, 518 rows, about 0.5 s per snapshot, 140 KB per file.

The copy still had one pending migration, `2026_10_31_000001_move_project_tasks_to_the_tasks_list`.
The compare reported it correctly: `tasks.list: values changed` (task 13 moved list) and
"1 problem, do not release". With `--ignore=tasks.list` (the change is intended) it said
"Nothing lost". So the tool catches real changes on a real file.

## The real dry run (needs Niels)

The refactor's own migrations (step 1.1 onwards) do not exist yet. The dry run is therefore done
**twice**: once now to prove the process on the current schema, and again with every migration
from phase 1 (gate of phase 1) and before the release (5.4).

**I never connect to production.** You make the copy; I only work on the copy.

1. **Make a dump** of production and restore it into a separate database that is not production,
   e.g. on the dev server: a new database `nothing_to_do_rehearsal`, or a SQLite file
   `database/rehearsal.sqlite` (both git-ignored patterns are in place).
2. **Point a separate env at it.** Copy `.env` to `.env.rehearsal` (git-ignored) and change only
   the `DB_*` lines to the copy. Every command below runs with `--env=rehearsal`, so the normal
   `.env` is never involved.
3. **Run the cycle:**
   ```bash
   php artisan app:rehearsal-snapshot before --user=<your email> --env=rehearsal
   php artisan migrate --env=rehearsal
   php artisan app:rehearsal-snapshot after --user=<your email> --env=rehearsal
   php artisan app:rehearsal-compare before after --env=rehearsal
   php artisan migrate:rollback --env=rehearsal
   php artisan app:rehearsal-snapshot rolled-back --env=rehearsal
   php artisan app:rehearsal-compare before rolled-back --env=rehearsal
   ```
   The first line prints which database it reads. Check that it is the copy.
4. **Spot-check your account** (TESTBERICHT C3): open the app against the copy and look for
   anything missing or changed.
5. Delete the copy and the snapshot files afterwards.
