# Spike 0.2 · Slot, session and capacity engine

Refactor plan step 0.2 (R4, R5, R9, R10; risks C2, C4, C14). Built 2026-11-06 on
`feature/engine-spike`.

**Gate result:** the engine passes its fixtures. 63 tests in `tests/Unit/Planning`, all green.
A mutation check (long break 5 instead of 15, wall-clock instead of real minutes, no soft-slip
pass, `<=` instead of `<` at the 5 minute threshold) made 1 to 4 tests fail each, so the
fixtures really guard the rules.

## What it is

Pure PHP in `app/Planning`. No database, no Livewire, no clock: every method takes its inputs
and "now". Phase 1 wires it to the models (1.2 week plan, 1.4 capacity, 1.6 categories,
1.7 sessions); the code here is meant to be kept, not thrown away.

## Decisions I had to make (please confirm or change)

These are not in REQUIREMENTS. Each is one line of code to change.

| # | Question | What the spike does | Why |
|---|---|---|---|
| E1 | A fixed appointment (no pomodoro) lies inside a pomodoro block. | **It cuts the block**: Deep work 19:30–21:30 with the dentist 20:00–20:30 gives 3 sessions, not 4. | You cannot work while at the dentist; otherwise capacity lies. |
| E2 | Two pomodoro blocks overlap. | Counted **once**; the overlap belongs to the block that **started first** (its areas apply). | Avoid double capacity (C4). |
| E3 | The long break counter and blocks. | Runs **across all blocks of the day**; a break pushes the next session even into the next block. | Q2 says "counted per day". |
| E4 | How big are Quick and Long? | **Quick = 10 min** (2–3 per session), **Long = 3 sessions** (upper bound of 2–3), Block = max(4, old estimate). | An optimistic forecast hides crunches (F4). Hysteresis in 1.4 keeps it from crying wolf. |
| E5 | Tasks without an area; categories without linked areas. | A task **without area fits any** pomodoro block. A category with **no linked areas** accepts only tasks without area. | "Training → none" means nothing from an area is suggested there. |
| E6 | Done with ≥ 5 min left but nothing else to do. | The **session ends** (back to the board); it does **not** count toward the fourth-session long break. | The work stopped early; counting it would make the long break come too soon. |
| E7 | After a break. | Phase **Ready**: the carried-over task waits for a tap on Start. No auto-start. | A session that starts on its own while you are away is the "app fills every gap" risk (F9). The old app had an autostart setting; we can bring it back as an option. |
| E8 | A session that runs over midnight. | Counts for the **day it started**. | Simple and matches "tonight". |
| E9 | A block across the DST change. | Start and end keep their **wall-clock** time (the grid shows what you typed); capacity uses **real minutes**. 01:30–03:30 on 25 Oct = 3 h = 5 sessions; on 28 Mar = 1 h = 2 sessions. | C2. Evening blocks are unaffected either way; this only matters at night. |
| E10 | Crunch: hard and soft deadlines compete. | Earliest deadline first. If a hard deadline is missed, hard work is planned **as late as possible** and soft work gets what is left; the soft task is reported as **slipped**. | R5 "soft deadlines are suggested to slip first". |

## Known limits (fine for now)

- `DeadlineFeasibility` is greedy. With area links an optimal split can exist that it misses.
  Good enough to warn; the crunch screen lets the user decide.
- Free time (outside all blocks, for R6 ideas) is not part of the spike. It needs the user's waking
  window, which does not exist yet; step 3.4.
- Early warning hysteresis and the soft-slip rule (G2) are step 1.4.
