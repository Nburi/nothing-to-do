# Spike 0.1 · iOS arrival trigger

Refactor plan step 0.1 (R2; risks F1, C1, C10). Server side built 2026-11-06 on
`feature/arrival-spike`. After the first test on 2026-11-17 the trigger is the **iPhone's location**
("Arrive" at home), not the home Wi-Fi; this guide was rewritten for that on 2026-11-23.
**The push on the phone is still to be seen** (TESTBERICHT C2).

**Question:** when Niels comes home, does a nudge arrive on its own, before he picks up the phone?
**Success:** 5 of 5 evenings without tapping anything.
**If it fails:** the time-based nudge from the week plan (step 3.3, already built) is the fallback in R2.

## What the first test showed (Niels, 2026-11-17)

| Trigger | Result |
|---|---|
| **Wi-Fi**: join the home network | **Failed.** After working on the train the hotspot was still on, the home Wi-Fi never connected, so the automation did not fire. |
| **Location**: "Arrive" at home | **Fired every time**, always at the same spot, about 60 seconds before he enters the house. |
| The push on the lock screen | **Not seen yet.** It needs VAPID keys on the dev server and the web app on the Home Screen. |

So location is the arrival trigger. Wi-Fi stays below as a documented fallback. The server does not
care which one calls it: it only sees `POST /api/arrival`.

## How it works

```
iPhone arrives at home (location)
  → Shortcuts automation runs "Get contents of URL"
  → POST https://<dev-server>/api/arrival   (Authorization: Bearer <arrival token>)
  → the server checks the evening rules (next section)
  → one Web Push to every device with notifications on
  → "Du bist zuhause · Zehn Minuten zurücksetzen, …" on the lock screen; tapping it opens /board?reset=1
```

- The call comes about **60 seconds before he is at the door**, so the push is already on the lock
  screen when he takes the phone out.
- The token can **only** call `POST /api/arrival`. Every other API route and `/mcp` answer 403 for
  it (`RejectNarrowTokens`), so a token copied out of the Shortcut cannot read or change tasks.
  Existing tokens are unchanged.
- At most 6 calls per minute.
- Every call is logged in `storage/logs/laravel.log`: `Arrival ping` (pushed: devices, delivered,
  status per device) or `Arrival ping held back` (with the reason). That tells where a missing nudge
  got lost.

## The evening rules

The arrival is the evening's nudge **sent early**, not an extra push. The location automation can
fire more than once in an evening (he leaves and comes back) and when he only passes by, so the
server decides with the same rules as the time-based nudge (step 3.3, `App\Services\Planning\EveningNudge`).
The answer is status 200 with `sent: false` and a `reason`, so the Shortcut shows no error.

| Situation | `reason` | Why |
|---|---|---|
| A nudge already went out tonight (an earlier arrival, or the time-based nudge) | `already_sent` | One nudge per evening; both paths share `evenings.nudge_sent_at`, whoever is first wins. |
| This weekday has no nudge time, or the card was never saved | `no_time` | Einstellungen › "Abschalten am Abend" is the off switch: no time, no push. |
| Paused day in the week plan | `paused` | R2: none on paused days. |
| Tonight's reset was already started or closed | `reset_done` | R2: none after the reset is done. |
| A focus session is running | `in_session` | Never into a focus block. |
| More than 2 hours before the nudge time | `too_early` | A lunch visit or a trip past the house at noon must not use up the evening's only nudge. |

A held-back arrival writes nothing, so the time-based nudge at the nudge time still comes. What this means
in practice:

- Set a nudge time for the weekday, otherwise the arrival stays quiet by design (`no_time`).
- If the time-based nudge went out while he was still away, the arrival has nothing left to send.
  Setting the time a bit later than the usual arrival lets the arrival come first.
- A server without push keys answers 503 (`push_unavailable`) and does **not** use up the evening, so
  adding the keys and arriving again the same evening works.

## Set up (about 10 minutes)

**1. The web app on the iPhone must be installed and allowed to notify.** iOS only delivers web
push to an app on the Home Screen (iOS 16.4 or newer).
1. Open the dev server in Safari, Share → "Zum Home-Bildschirm".
2. Open the app **from the Home Screen icon**, Einstellungen → Mitteilungen → turn them on and allow.
3. Send the test notification from the same settings section. It must arrive before you go on.
4. Einstellungen › "Abschalten am Abend": set a time for the weekdays you want the nudge on.

**2. Create the token** on the dev server:

```bash
php artisan app:arrival-token <your email>
```

Copy the token it prints; it is shown only once. It appears in the app under
Einstellungen › Shortcuts, API & MCP as "iPhone: Ankunft zuhause · Nur Ankunft melden", where you
can revoke it.

**3. Build the automation** in the Kurzbefehle app (labels can differ slightly between iOS versions):
1. Automation → + (new personal automation) → **Ankunft** → choose your home as the place
   (search the address, or use the current location while you are at home) → **Jederzeit**.
2. Choose **Sofort ausführen** and turn **Bei Ausführung benachrichtigen** off. Without this, iOS
   asks for a tap and the test is pointless.
3. Action **Inhalte von URL abrufen**:
   - URL: `https://<dev-server>/api/arrival`
   - Methode: **POST**
   - Header: `Authorization` = `Bearer <token>` and `Accept` = `application/json`
4. If iOS asks whether Kurzbefehle may use your location, allow it: the automation runs in the
   background. Ortungsdienste must be on.
5. Optional while testing: add **Ergebnis anzeigen** after it to see the server's answer
   (`sent`, `reason`, `message`, `devices`, `delivered`). Remove it for the real evenings.

**The hotspot case:** with the location trigger nothing depends on Wi-Fi. It does not matter
whether the phone's hotspot is still on after the train or whether the home network ever connects.

## Fallback: Wi-Fi trigger

Same setup, but in step 3.1 choose **WLAN** → the home network → **Beim Verbinden**. **Known
weakness (2026-11-17):** it did not fire reliably. After the train the hotspot was still on, the
home Wi-Fi never connected, so the automation never ran, and the server saw no call at all. Use it
only if location is not an option. The server rules above are the same for both triggers.

## The test

**Quick check:** with the phone locked, walk a few hundred metres away from home and come back
(the location automation fires when you enter the area again). Look at the answer and at the log.
Do it **once** per evening: a second arrival the same evening answers `already_sent`, which is the
rule working, not a bug.

**Reading the result**

| What you see | Where it broke |
|---|---|
| No log line | The automation did not run (iOS did not fire "Arrive", it still asks for a tap, or location permission is missing). |
| `Arrival ping held back`, `reason` ... | The rules kept it quiet, see the table above. `already_sent`: the time-based nudge was first. `too_early`: more than 2 hours before the nudge time. |
| `Arrival ping`, `delivered: 0` | Push delivery (VAPID config, subscription gone). Check the test notification in settings. |
| `Arrival ping`, `delivered ≥ 1`, nothing on the phone | iOS hid it (Focus mode, notification settings of the web app). |
| `devices: 0` / answer 409 | No push subscription: step 1 again, from the Home Screen icon. |
| Answer 503, `push_unavailable` | The dev server has no working VAPID keys (`.env`). |
