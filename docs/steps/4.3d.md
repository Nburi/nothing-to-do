# Step 4.3d: project management gaps (delete, stage order, board tasks in and out)

Branch `feature/project-manage`, based on `refactor/refactor` (4ae57e2). Closes the TODO item "Projects/groups: delete,
reorder stages, move an existing board task into a project or group" (see also 4.3 decision 7 and 2).

## Data and migration

None. No new column, no migration, nothing dropped. Everything uses `tasks.project_id`, `group_id`, `stage_id`,
`waits_on_id`, `project_stages.sort_order` as before.

## How it works (all in `App\Services\Projects\ProjectEditor`, pages call it through `ManagesMembership`)

**Delete** (entry in the ⋯ menu of the page header since ui-fixes, was a button at the end of the page; behind an in-app confirm `shell/confirm-delete.blade.php`; no native `confirm()`):
- **No task is lost.** Every task of the project (open and done) loses project, stage and "wartet auf" and stays in its own
  list (Inbox, To-dos, Tasks, Later). A group's tasks lose `group_id` and stay in their list.
- **What goes:** the project's stages and note cards (DB cascade). The confirm names both with their numbers and says it
  cannot be undone. There is no undo for a delete, on purpose: the confirm is the safety.
- A group a project was made from at the switch (`task_groups.project_id`) is deleted with the project; otherwise the FK
  `nullOnDelete` would turn it into a group again and pull its old tasks back in. Its tasks lose `group_id`.
- `event_categories` that linked the project or group get `task_source = null` (the FK nulls the id; the old reset hook is gone).
- A failed delete (any exception) is reported with one plain line in the dialog; nothing is deleted (one transaction).
- Success: redirect to the Projekte page with a one-time line ("... Die 3 offenen Schritte liegen wieder auf dem Board.").

**Stage order:** two buttons per stage (up/down, hidden with only one stage) call `ProjectPage::shiftStage`
-> `ProjectEditor::moveStage`. Stages are numbered 0..n-1 again under a lock; a move that changes nothing says nothing.
A "wartet auf" link whose waiting step now sits in an earlier stage than its blocker is let go (same rule as 4.3c, now for
the whole project); the toast says so and "Rückgängig" restores order and links (`restoreStageOrder`). The board's
current stage and next two follow the new order automatically (`NextSteps` sorts by `sort_order`).

**Board task in:** button "Vorhandene Aufgabe" opens a picker (`shell/task-picker.blade.php`): search (debounced), first 30
matches, "N weitere", optional target stage (projects). Offered: open tasks of the user on no project or group and not
recurring (a step is done once). A group takes only tasks of its own list. The task keeps its list and everything else and
goes to the end of the stage. `ProjectEditor::adopt` re-checks all of it on the server (foreign id, foreign stage, wrong list
-> "Das gibt es nicht mehr").

**Step out:** ⋯ menu item "Zurück aufs Board" (`releaseStep`): project, group, stage and links are cleared (steps waiting on
it are freed); it stays in its list. "Rückgängig" puts it back (stage if it still exists, same place; links where nothing
changed since; refused calmly if the task moved on).

## Decisions Niels should check

1. **Delete takes stages and note cards with the project.** Tasks never go. Is that the right line for notes?
2. **Released steps keep their list**, so a big project can put many steps on the board at once (the confirm says so). Alternative: send them all to the Inbox.
3. **Stage order by buttons, not drag.** Stages are few; the buttons work on touch and keyboard. Dragging a stage could follow.
4. **Moving in is offered on the project and group pages only.** A "Zum Projekt" entry on the board's own task menu is a change in `Board.php` (the To-do session works there), left out.
5. A task that already sits in a group cannot be pulled into a project directly (release first).
