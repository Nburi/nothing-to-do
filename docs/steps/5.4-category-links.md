# Step 5.4 · Board follow-ups: day list under the To-do card, drag for stages, category links

Built 2026-11-27 on `feature/board-followups`, from `refactor/refactor` at `57b2311`. Three things Niels decided in the
review artifact (decisions `d37-multi` "plan", `d36-order` "drag", `d-catlinks` "suggest").

## 1. The work block under the To-do session card (`d37-multi`)

Niels: "Gerne vielleicht unter der Karte eine Liste mit allen Aufgaben die in diesem 'Arbeiten-Block' geplant sind."

Under the To-do session card the board shows a quiet, foldable list: **what the engine plans for the rest of today's work
block** (the pomodoro block running now, else the next one today), session after session.

| Piece | What |
|---|---|
| `Suggestions::blockPlan()` | Takes today's 25 minute slots that are still ahead, keeps the ones of the first slot's block, ranks the open work with the pick engine (the block's category: area filter, link, hidden steps) at battery Okay, and fills the slots one after the other with `TodoBundler::bundle()`. No second planner: the ranking is the pick's, the filling is the To-do session's. |
| `TodoBundler::slotsOf()` | A bundle takes one slot, a single task longer than a slot takes `ceil(minutes / 25)` slots. |
| `BlockPlan` | Name of the category, from/to of the block, `running`, the filled `sessions` (start, rows with minutes), `waiting` (what does not fit into the block today). |
| `TodoSession::$block` | The plan travels with the card, so both layouts and the session peek get it without more wiring. |
| `shell/todo-session.blade.php` | The list inside the card, under a hairline: heading "Heute im Block „Arbeiten“", the block times, count and minutes, one row per session (time, tasks with minutes), "+ n weitere passen heute nicht mehr in den Block". The heading is a 44 px button that folds the list (Alpine, not saved). Open by default. |

Rules and edges:
- Not tied to the evening battery (always Okay), so the list does not jump when tonight's question is answered. The
  *pick* still follows the battery.
- Only the steps the board shows are listed (NextSteps: the next two of a project or group), like the pick.
- The first slot of the list is not the card's session: the card bundles loose To-dos only, the list ranks every kind of
  work for the block. They can show the same To-do twice; the heading says which one is the block.
- No work block left today (after the last slot, a day without blocks, Saturday): no list. A card without To-dos has no
  list either (it hangs on the card).
- Query budget: no new query. The plan reads the one `PlanningContext` the board already built. `/board` stays under 40.

## 2. Stages by drag (`d36-order`)

Niels: stages reorderable by drag **in addition** to the buttons (they stay: touch and keyboard).

`resources/js/board-order.js` (step 4.8) now takes two options: `method` (the Livewire method that saves, default
`reorder`) and `zone` (a selector inside each entry that is the lift handle and the ghost). The project page wraps its
stage sections in `x-data="boardOrder({ method: 'reorderStages', zone: '[data-stage-head]' })"`:

| Input | How |
|---|---|
| Mouse | Drag the grip (the new `⋮⋮` button before the arrows of a stage's heading). Starts after 4 px. |
| Touch | Press and hold the **heading** (350 ms). Only the long press lifts, a swipe scrolls. A hold on a step is the step lift of 4.3c, not a stage lift. |
| Keyboard | Space on the grip lifts, ↑ ↓ move, Space drops, Escape cancels, every change is announced in the live region. |

While a stage is lifted only its heading line (not the stage with all its steps) follows the pointer as a ghost and a
dashed slot shows the place; the stages stay in the page. The last section (steps in no stage) is not a stage and cannot
be moved or be passed.

Server: `ProjectPage::reorderStages(array $refs)` receives `stage:ID` for every stage in the new order, finds the one
stage whose removal leaves both orders equal and places it through the same path as the buttons (`ProjectEditor::moveStage`:
numbered again under a lock, a "wartet auf" that now contradicts is let go, one toast with "Rückgängig"). A list that does
not match the project's stages (one added or removed meanwhile, a foreign id, no change) changes nothing and the page is
redrawn with what the server has. `step-drag.js` ignores the keys of a stage grip (it has no step).

## 3. Category links (`d-catlinks`)

Niels: after the switch a production category linked to a project, group or Agenda entry should **suggest this project's
or group's next steps in this block**.

### How the old links were stored

`event_categories` (migration `2026_08_23_000001`): `task_source` (`project`, `group`, `tasks`, `agenda_entry`,
`agenda_generic`, `text`), `linked_project_id` → `projects`, `linked_group_id` → `task_groups`,
`linked_agenda_entry_id` → `agenda_entries` (all `nullOnDelete`), `linked_text`; pinned tasks in `category_task_links`.
The REST API and the MCP tools `set_category_task_link` / `clear_category_task_link` only know `tasks` and `text`
today (the project/group/Agenda sources can no longer be set anywhere: only old rows carry them).

### What the pick engine does now

`EventCategory::toPlanningCategory()` hands `Category` the linked project (`task_source = project`) or group
(`task_source = group`). `PlannedTask` carries `projectId` / `groupId` of the task. In `PickEngine::rank()`:

- Tiers are now **0** late / starts today, **1** has a deadline, **2** a step of the linked project or group, **3** marked
  „Wichtig", **4** the rest. A link never jumps a deadline (also not a soft one); two tasks on the same date and hardness
  prefer the linked one after „Wichtig".
- A step of the link passes the **area filter** (the link is the more specific statement); every other task still obeys it.
- The pool is already cut to the steps the board shows (`NextSteps` hidden steps are excluded), so a project's third step
  and the steps of a resting card are not suggested. Not exclusive: without a linked step the normal ranking decides.
- The reason is "Der nächste Schritt für das, wofür dieser Block gedacht ist." (`pick.why.linked`).
- The block plan (1.) uses the same ranking, so linked steps stand first in its sessions.
- A group that became a project at migrate (mixed group, `2026_11_17_000004`) keeps its `group_id` on every task: a link
  to it still matches.

### The data path (migration `2026_11_27_000001_map_category_links_to_the_new_engine`)

| Old link | After the switch |
|---|---|
| `project` / `group` | **Unchanged.** The engine reads the same columns. Nothing to move. |
| `agenda_entry` | `task_source = text`, `linked_text` = the entry's title (a label already there stays), `linked_agenda_entry_id` stays, `legacy_task_source = agenda_entry+label` (the `+label` marks a label this migration wrote, so `down` removes exactly that). |
| `agenda_generic` | `task_source = text`, `linked_text = 'Agenda'`, `legacy_task_source = agenda_generic+label`. |
| `tasks` (pinned) / `text` | Unchanged. Pinned tasks stay in `category_task_links`; the new engine does not use them (open question, `TODO.md`). |

New column `legacy_task_source` (nullable string, additive). Nothing is deleted; `down()` puts the Agenda sources back.
The runbook's D1 is decided as option (c); `app:switch-preflight` counts these categories as a NOTE now.

### The category editor (Einstellungen › Kategorien)

Under the linked areas of every pomodoro category: a select "Nächste Schritte vorschlagen aus" with "Nichts Bestimmtes",
the user's **Projekte** and the **Gruppen** that are still a group. `Categories::setLink()` ignores anything that is not the
user's own project or group and anything that is not a category of the user. Choosing a link keeps the old text and pins
(only the active source changes); "Nichts Bestimmtes" only ends a project/group link and never touches a text hint. A
text hint of an old link shows as "Alter Hinweis: „…“" under the select.

## Not done here

- REST API and MCP cannot set a project or group link (`set_category_task_link` knows `tasks` and `text`); the `api-parity`
  session works in that area, so it is left alone. Reading `linked_project_id` / `linked_group_id` in `EventCategoryResource`
  belongs there too.
- Pinned tasks (`task_source = tasks`) are still not used by the new engine. Same idea would fit ("these tasks first in this
  block"); not asked for.
- A link to a project whose card rests on the calm board suggests nothing from it (its steps are hidden). Waking it up by the
  link would be a rule of its own.
