## How it works

| Piece | What |
|---|---|
| `App\Services\Planning\SundayReview` | Read-only. `reviewedMonday()`: on Sunday the week that ends today, on any other day the last full week. `offeredOn()`: Sunday and Monday. `for()` returns `past` and `next`. |
| Past | Per-day counts from `ProgressStats::completedCountsByDay()` (the old review and the Fortschritt heatmap read the same). Judgement from `WeekReview::judge()`. Finished titles newest first with area, bucketed by local day with the offset at that instant. Later ideas done, items captured (`created_at` in the week), resets (`evenings.reset_started_at`), the current inbox count, open tasks whose hard or soft date fell in the week. |
| Next | The seven days after the reviewed Sunday. Room = `capacitySessions` from `Capacity::forecast()`, load = planned minutes / 25 rounded up, `over` = minutes over room / 25 rounded up. Pause days from `schedule_pauses`. Days before today count as "vorbei". `tight` = the first overloaded day. Deadlines due in those days. |
| `WeekReview::judge()` | Extracted from the old `verdict()`. Returns the kind (`nothing`, `running`, `running_first`, `best`, `first`, `above`, `below`, `usual`) and the average. The old page still builds the same German sentences from it (WeekReviewTest unchanged and green). |
| `App\Livewire\Shell\Review` + `livewire/shell/review.blade.php` | The page. `shell/review-dated.blade.php` renders the dated rows, `shell/review-line.blade.php` the board line. Strings in `lang/{de,en}/shell.php` → `review`. |
| `Shell\Board::reviewOffer()` | `'sunday'`, `'monday'` or null, from the user's local date (`UserClock`). |

No migration, no new `.env` key, no new action in the registry.

## Decisions to check

1. **Sunday is judged as a finished week.** The old review never compares a running week. On the review day the comparison with your average is the point, so the new screen compares on Sunday too. Things finished later on Sunday evening count when you reload.
2. **"sortiert" from the preview became "noch in der Inbox".** The app stores no time for when an item was sorted, so a "sorted this week" number would be a guess. The screen shows what was captured in the week and what still waits in the inbox now.
3. **Sessions are not counted.** Past pomodoro sessions are not stored (`pomodoro_sessions` holds only the running one). The review counts finished things. A session log would need a new table, so it is left out.
4. **The line stays on Sunday and Monday, even after you opened the review.** Hiding it after one visit would need stored state. It is a quiet dashed line, so it stays simple.
5. **Links that depend on siblings.** "Ansehen" in the tight line goes to `/board?crunch=1`, which opens the crunch screen once 4.2 (PR #23) is merged; until then it just opens the board. "Woche anpassen", "Woche planen" and the Stapel tab "Kalender" go to `route('shell.week')` once 4.1 (PR #24) is merged, and to the old `/app/weekplan` until then (`Review::weekUrl()`).
6. **An overdue hard deadline counts on today.** That is how the forecast plans it (step 1.4), so on a Monday with an overdue fixed task the right half can name today as too full. It shows the same thing the crunch warning sees.
7. **Hard before soft.** If a task has both dates, it is listed by its hard date ("fix"). Soft dates are never red.
