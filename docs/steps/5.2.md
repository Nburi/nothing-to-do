# Step 5.2 · Accessibility, reduced motion, performance
Refactor plan step 5.2 (R7, risk C7). Built 2026-11-25 on `feature/a11y-perf`, from `refactor/refactor` (`4ae57e2`).
No visible design change beyond what accessibility needs: the touch targets on the phone got bigger, the rest looks the same.

## How it was audited
- **axe-core 4** (WCAG 2 A/AA, 2.1 AA, best practice) on `/board`, `/board/week`, `/board/week/plan`, `/board/review`,
  `/board/projects`, `/board/ideas`, `/board/settings` at 1280 px (Werkbank) and 390 px (Stapel), with a seeded account (696 tasks,
  8 projects, 3 areas, a week plan, 14 appointments), plus the overlays opened: sort card, capture sheet, pause sheet, Stapel list sheet.
- A **keyboard walk** (Tab / Shift+Tab / Enter / Escape only) through skip link, start, session, peek, stop, capture, in both layouts.
- A **focus probe** per overlay: where the focus goes on open, whether 25 Tab presses leave it, whether Escape closes it, where the focus is afterwards.
- Own checks: every visible control's size (the hit area counts), accessible names, focus ring on every Tab stop, landmarks.
- Scripts live outside the repo (scratchpad); the results are in the table. Real screen readers were not run, see C90.

## Reduced motion
- One global rule collapses every CSS transition and animation to 0.01 ms (toasts, sheets, fades, the timer fade), the fold has its own rule (`.shell [data-region="board"] *` etc.).
- JS: the fold, the ghost card, the fold hand-over and the step drag ask `matchMedia` first; the one remaining `scrollTo({ behavior: 'smooth' })` (Desk tab) now asks too.
- **The fold under reduced motion** (CONVENTIONS 10): no `shell-folding`, no ghost, no animation. The board stays until the server's answer is there, then the session card is simply there,
  the board is the rail/drawer, and **the focus is on the page heading "Session läuft: <task>"**, which is what a screen reader reads out. Going back to the board puts the focus on "Board".
  That is the instant, readable equivalent. Measured with Playwright `reducedMotion: 'reduce'` at 1280 and 390 px:

| | no preference | reduce |
|---|---|---|
| `shell-folding` set | yes | **no** |
| elements with a transition > 50 ms | 647 | **0** |
| running animations > 50 ms | pulse dot, fold-return card, piles | **0** |
| session card up after Start | 0.85 to 0.93 s (server) | 0.75 to 0.79 s (server only) |
| focus after Start | page heading | page heading |
Screens: `docs/screens/5.2-session-{werkbank,stapel}-{normal,reduced}.png`.

## Performance
Seeded account: 696 tasks (180 To-dos, 196 Tasks, 120 Later, 39 Inbox, 100 done), 8 projects with 12 steps. PHP built-in server, SQLite, no HTTP compression.

| | before | after |
|---|---|---|
| `/board` queries | 51 (28 duplicates) | **33** |
| `/board` week plan reads (templates, events, pauses) | 4 | **1** |
| `/board` HTML | 1 200 KB | **1 059 KB** |
| `/board` server time (warm) | 540 ms | 510 ms |
| `/board/week`, `/plan`, `/projects`, `/settings` queries | 12, 9, 9, 9 | unchanged (no N+1) |
| `/board/ideas` queries / HTML | 14 / 451 KB | unchanged |
| JS (gzip) | 98.8 kB (32.1) | 100.7 kB (32.7): the new directive and the error linker, +2 kB |
| CSS (gzip) | 142.5 kB (24.0) | 144.7 kB (24.4) |
| First paint, 390 px, "slow 4G" + CPU ×4, cold | not measured before | FCP 0.9 s, load 4.7 s |
| First paint, 1280 px, same throttle | not measured before | FCP 3.0 s (the 1 MB HTML is parsed first), load 7.4 s |

What was fixed:
- **Plan read once per render.** The pick, the free-time idea and the crunch each built their own `PlanningContext` (all open tasks, categories, blocks, slots); the time line read the week plan a fourth time.
  `Board` now has one `planning` computed property, handed to `Suggestions::current`, `FreeTimeIdeas::current` and `CrunchOverview::for` (new optional parameter, old callers unchanged) and dropped by `fresh()`.
- **Task row buttons as one class.** Every row carried two 600-character utility lists (flag, start); `.task-action` writes them once: −150 KB of 1 200.
- **Guards:** `ShellQueryBudgetTest` runs every shell page with 10 and with 60 tasks per list and fails if the query count differs (an N+1) or goes over a ceiling; `/board` must read the plan tables once.

What is **not** fixed, on purpose:
- `/board` is still about 1 MB for 700 tasks and every Livewire action returns it again. The cause is that both layouts and the Stapel list sheet are rendered (each up to 40 rows per list) and CSS picks one.
  A cookie with the layout (set by JS, re-read on a breakpoint change) would let the server render the other layout as an empty shell: about −45 %. That changes what is in the DOM per device (the parity test A11 reads both),
  so it needs your decision, not a quiet change. A user with 100 tasks is at about 200 KB and 120 ms, which is fine. Proposed as a later step.
- `/board/ideas` shows all of Later as cards (454 KB for 120). Paging or "show more" would change what is on the page.
- An icon sprite instead of inline SVG was tried and dropped: the saving was 6 KB, because the `<svg>` wrapper is most of the bytes.
- Fonts: the browser only loads the faces of the active theme (2.1); nothing to do.
- The oldest phone (risk C7) was not available to Claude: C92.

## Decisions I made (please check)
- **x-trap without `inert`** for the sheets: the page behind stays in the accessibility tree but the focus is held and `aria-modal` says it is behind. Alpine's `inert` modifier also touches the toast container and the live regions.
- **The Stapel list sheet traps below 720 px only.** It sits hidden in the desktop markup too, and its trap pulled the focus off the Werkbank peek panel (found with the keyboard walk).
- **44 px on the phone, desktop unchanged.** The mouse sizes stay; the phone rows grow by a few pixels. Small text links keep their look and get the hit area.
- **Out-of-month days in the pause calendar** are `ink-faint` without the 50 % opacity (2.1:1 before). They look a bit stronger.
- **Battery chip:** `aria-pressed` toggles instead of a menu role. A real menu would need arrow keys; three buttons do not.
- **The reset screen's title is an h2** now, the page keeps its h1.
