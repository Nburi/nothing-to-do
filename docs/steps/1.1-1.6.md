# Steps 1.1 and 1.6 · Task model, categories and areas

Refactor plan steps 1.1 (R5, R8; risk C6) and 1.6 (R10; risk C3), data layer only. Built 2026-11-07,
stacked on `feature/engine-spike` (PR #3) because the models map onto its `App\Planning` types.

## What changed

| Piece | What |
|---|---|
| `areas` | New table: `user_id` (cascade), `name`, `color` (one of `ScheduleEvent::EVENT_COLORS`), `sort_order`. Model `App\Models\Area`, `User::areas()`. |
| `category_area` | Pivot category ↔ area, cascades both ways. `EventCategory::areas()`, `syncAreas()` drops ids that are not the owner's own areas. |
| `tasks.size` | `quick` / `short` / `long` / `block`, cast to `App\Planning\Size`. **NULL for every existing row**: "not sized yet" stays visible to the daily sort; the engine reads NULL as Short (G1). The plan said "default short" — a default would make every old task look deliberately sized. |
| `tasks.hard_deadline`, `tasks.soft_deadline` | First half of the two-step rename, backfilled from `deadline` / `due_date` with the query builder (no `updated_at` bump). |
| `tasks.area_id` | Nullable FK, `nullOnDelete`: deleting an area never deletes a task. |
| `Task::booted()` | Mirrors old ↔ new deadline columns on every Eloquent write; the new column wins if both change and disagree. |
| `Task::toPlannedTask()`, `EventCategory::toPlanningCategory()` | The bridge to the engine. `duration_minutes` becomes the session estimate a Block needs. |
| Reads | `Task::effectiveDate()` and `isUrgencyLocked()` now read the new columns. Raw-SQL reads (`scopeBoardOrdered`, `DayPlanner`) still read the old ones — equal by the mirror, switched in the follow-up. |

Existing `event_categories` need no migration: `pomodoro_enabled` already is the "pomodoro sessions"
switch. A category without area links accepts only tasks without an area (E5), so nothing changes for
existing users until they create areas.

## Data safety

- Both migrations are additive. `down()` drops only the new columns; the old ones still hold the data.
- Tested: rows shaped like production's (only old columns filled) migrate with the same row count and
  identical dates, and `updated_at` is untouched (`TaskModelTest`).
- **Not done:** a dry run on a real production copy (step 0.3, needs the dump). Also, prod runs `main`,
  which has 21 migrations `refactor/refactor` lacks; these two only touch `tasks` columns that exist on
  both, so they apply cleanly either way.
